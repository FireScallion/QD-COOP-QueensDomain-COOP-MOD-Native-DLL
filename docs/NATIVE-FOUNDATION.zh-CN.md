## 已实现的边界

### 成员与生命周期

`native/src/session.cpp` 是房主侧四人成员模型。使用房间 ID、稳定玩家 ID、每次连接代次和世界代次，支持二、三、四人。满房只拒绝新成员；重复加入不产生第二个成员。重连获得新连接代次，旧连接消息失效；其他成员状态保留。新成员和切图成员先处于 loading，只有恢复本地世界后才能标记 active。一个慢客机不会阻止其他成员 active。

房主退出关闭房间，不做房主迁移。断线玩家的倒地状态和倒地代次保留，重新加入或切图不自动复活。模型最多记录一个房间生命周期内 64 个不同身份；容量满后返回明确 backpressure，已有身份仍可重连，不淘汰历史记录。这是有界原型限制，后续可在维持旧身份拒绝/恢复语义下调整。

### 每对端通道

`native/include/qdcoop/channels.hpp` 提供每连接独立的可靠发送队列、按序应用收件队列、最新快照槽。关键事件队列为 64 条，每条载荷最多 512 字节；数据自有，不持有外部内存或 UObject 指针。当前载荷上限适用于模型测试，大世界快照分片和不同事件类别仍需独立设计。

队列满会返回 backpressure，生产者必须保留意图并稍后重试。接收窗口外的关键事件不会被假装成功接收。收件者只有在实际应用成功后推进应用序号；缺少前序时缓冲后序。快照可覆盖旧值，拒绝旧序号、错误连接和错误世界。传输 ACK 只释放传输缓存，不代表扣药、复活或存档已完成。未来适配层必须通过重连世界基线与持久事务恢复处理接收进程崩溃。

这些是数据模型与调度逻辑；Steam、UDP socket、握手认证、跨线程命令队列、世界分片尚未接入。

### 救援仲裁

`native/src/transactions.cpp` 在 E 蓄力完成时仲裁同一倒地对象，检查施救者、被救者、连接、世界和倒地代次；同一施救者不能同时发起多个未决救援。第二名施救者不会得到可扣药的事务。item=0 保留徒手 1HP 语义，1..6 对应现有药物代码；具体治疗量、当前选中道具、库存、瞄准、距离、持续按住 E 和中断判断仍由未来游戏适配层实现。

状态为 reserved → intent_durable → debit_durable → completed。适配层必须先持久化意图，再执行并记录幂等扣药，再执行并记录幂等复活。未有持久意图可取消；意图已持久化后，扣药指令可能已执行，断线或取消进入 recovery_required，不自动退款，不释放锁给另一个施救者。重复相同回执不重复执行，冲突回执被拒绝。

**当前仅实现仲裁与恢复阻塞状态，没有实现原生日志落盘、进程重启读回、道具余额核对或恢复解除。** 回执是测试/受信任适配器提供的证据，不能直接相信网络传来的“已落盘”布尔值。该限制意味着原型不能用于正式存档，也不代表既有 Lua 恢复能力已迁移完成。

### 共同检查点与全员倒地

任何 active 且存活成员可请求共同保存。存在 loading 成员时暂缓；开始时固定全体 active 成员、连接代次、世界代次、房主世界快照版本和成员版本。每人必须提供绑定该事务/快照版本的不可变存档副本完成回执，再由房主提供提交日志的持久回执，才成为 latest。四人时房主加两名客机完成仍不够。保存中加入、退出、重连或切图会中止本次保存，保留上一完整检查点；下一次重新确定参与者集合。快照版本的实际生成及回执内容核验由后续适配器负责。

全员倒地门控仅在新 DOWN 事件后评估，loading/断线成员不计入。重复 DOWN 或成员退出不重复触发；恢复完成才释放门控。最新检查点必须包含当前所有 active 身份的角色副本，否则暂不发出恢复指令，防止迟加入者没有角色档案仍假装完整回滚。

**读取真实游戏档案、各机文件持久化、分布式恢复完成确认、迟加入基线/检查点生成策略尚未接入。** 门控只输出待恢复的检查点 ID，不退主菜单，也不自行操作游戏。

## 验证与限度

- GCC 16.2.0，C++20，`-O2 -Wall -Wextra -Wpedantic -Werror`；禁用 RTTI/异常，静态链接编译器运行库。
- 实际构建并 LoadLibrary 加载 Windows x64 DLL，走公开 C ABI 执行一主三客、满房、重连、旧消息拒绝、切图、房主退出。
- 核心测试覆盖上述成员、通道、救援、共同检查点和全员倒地边界。
- 可靠通道仿真使用三对端 × 每端 200 个事件 × 五个随机种子，分别模拟约 30% 数据包与 ACK 丢失，以及延迟/乱序；要求事件按序恰好应用一次并最终清空待确认队列。
- 测试在独立控制台进程内运行，不启动游戏、不操作桌面、不读写任何真实存档。
- DLL 依赖检查要求只导入 Windows 的 KERNEL32.dll 和 msvcrt.dll；测试 PATH 排除编译器目录，避免漏带运行库被掩盖。没有 UE4SS、Lua、.NET 依赖。
- **以上只能证明原生基础库与仿真模型；不证明游戏联机功能迁移完成，也不证明帧率提升。** 本轮没有游戏性能采样，没有真实 Steam 多账号或跨机器测试。

## 后续实现顺序

1. 完成 `GameAdapter` 的最新正版构建识别、游戏线程入口、对象登记/失效和属性元数据验证。高频路径不得重新全表扫描 UObject；不能直接把现有 qdcapture 对 UE4SS 的导出调用照搬后称为解除依赖。
2. 选择敌人状态的一条完整采集—原生缓冲—时间线—应用路径，在独立正版副本上保持现有采样，验证弱句柄失效、切图及同地点整帧性能。这一阶段才进入 M1。
3. 接入真实 Steam/LAN、三名远端角色及原生动作资源，并将队列与会话模型连接起来。身份认证及三条独立链路必须由真实适配层实现。
4. 实现原生持久化/恢复适配器，再迁移救援、共同检查点、战斗奖励和世界剧情。当前恢复阻塞状态必须有经验证的安全解锁流程，才可进入可玩版本。
5. 保留现有菜单、五皮肤、原动作/武器/特效、经验掉落、机关/Boss/CG/传送规则，最终解除 QDCOOP 的 UE4SS/Lua/外部桥接依赖。其他 Mod 是否使用 UE4SS 不属于卸载范围。

此阶段不改难度数值，不降低采样率，不修改旧预览版的玩法实现。
